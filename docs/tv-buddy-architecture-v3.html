TV buddy v3: planes, the bounded agent loop, the rolling profile, the trace tree

Media rides WebRTC across the top and back. Control rides its own WebSocket. One Pipecat pipeline per session; the agent is a Pipecat LLMService that streams one strict JSON envelope per cycle, speaks say sentence by sentence while actions[] dispatch in parallel, and runs a bounded loop — at most AGENT_MAX_CYCLES round trips, the cap enforced by the last cycle's schema rather than by a runtime guard. A follow-up cycle's first-byte budget is opt-in (CYCLE_FIRST_BYTE_S=0) with a templated answer behind it. Everything that can wait — the memory ingest, the profile fold, history writes, status events, spans — is fired and never awaited.

One turn, from frame to frame

SGRAgentService._turn assembles the prompt and hands the cycles to TurnRunner.run: recall, prompt, cycle 1, then a follow-up cycle for every observation that earns one, up to AGENT_MAX_CYCLES. say leaves the model before actions[], so the viewer hears “On it.” or “Let me look.” while the command or the tool is still on its way — there is no canned filler any more. Before say the envelope decodes request — {operation, title, title_id} — and every action is then checked against it, so a lookup finishes the request it came from: “watch Moon” ends in play, “show me Moon” in open_details, “do you have Moon” in show_titles, and an action that serves some other operation never reaches the TV.

awaited, inside the turn fired, never awaited memory injected into the prompt

The same turn, as one trace

OpenTelemetry is the only instrumentation API; Langfuse is an OTLP/HTTP sink, never an SDK. Pipecat emits conversation → turn → stt / tts; everything of ours hangs underneath through one observation() helper, so no span can forget to declare its Langfuse type. Off by default, and never on the media path: a span is an attribute write, and both the batching and the content redaction happen on the export thread — the redactor is a SpanExporter inside the batch processor, not a processor that would rebuild every span inside span.end() on the turn's own task.

an LLM call — priced and token-counted in Langfuse outside the turn's tree

Why the loop is bounded. A voice interface cannot afford an open-ended tool loop. Cycle 1 always speaks something. A follow-up cycle happens only when a cycle produced an observation — an internal tool's reply, a successful catalog search, or any awaited action that failed. The last allowed cycle is decoded against a schema whose actions union has no observation-returning tools, so the model cannot ask for more and the loop always ends in speech — the cap is the schema's, not a runtime guard. AGENT_MAX_CYCLES is a setting (1–4, default 2), not a hand-unrolled second cycle: each extra cycle is a full round trip the viewer hears as waiting. The first-byte budget is now opt-in: CYCLE_FIRST_BYTE_S=0 by default, so a slow follow-up cycle is waited out rather than overtaken by render_fallback; a positive value buys the templated answer back. search_catalog likewise waits with no default deadline — a TV that never answers is the TV's bug to show, and a barge-in releases the wait as cancelled, which is never an observation.

The request is decoded, not inferred. The cascade is the field order: intent, then request — operation (play, open, lookup, discover, shop, control, answer), the title the viewer named verbatim, and its title_id if any supplied section or tool result lists it — then say, then actions[]. Because request closes before the first action streams, action_violation can check each action against it in code: play does not serve a lookup, show_products does not serve a watch, and play / open_details / show_products need the id the request decoded — a null title_id means “search first”, never “guess”. A violating action is rejected exactly like an unparseable one: the viewer hears say, and nothing they did not ask for happens. This replaced ~4 KB of prose that restated the same policy three times and was ignored on the very cases it was written for — “I want to watch Barbie” answered with recommendations.

One registry, two kinds of action. agent/envelope.py holds one ActionSpec per verb — TV or internal, whether the turn blocks on the reply, whether that reply is an observation the model must see, and how the prompt's capability manifest describes it. Thirteen TV verbs and two internal tools today. The envelope's actions[] union, the JSON Schema used for constrained decoding, the manifest and the TV app's TypeScript all derive from it, and dispatch matches on the parsed union member rather than on a verb string — each streamed action is validated against the union its own cycle was decoded with, so a canned final-cycle envelope carrying an observation tool is rejected instead of dispatched. Item commands carry a title_id the model copied from # Screen, # Recent activity, # Shop, a recommendation or a search result; the bus validates and enqueues but never resolves.

Four stores, kept apart. The catalog and its embeddings never enter memory. The viewing log is behavioural: it becomes the taste vector, the never-watched and never-declined filters, and the # Recent activity lines — with ids, which is what makes “yes, play it” work for a title that is not on screen. The profile holds only what the viewer is like, and the summariser is told the TV keeps its own log, so a stray line can shade the tone but never pick the film. The shop shelves are the backend's own file and reach the prompt as # Shop, keyed by the same title_ids — merchandise never becomes taste. Screen state is per-turn context and reaches none of them.

What changed since this diagram's first draft (the loop refactor, the TV control branch and the named-title routing work):

  • show_titles is the thirteenth verb. focus can only highlight a tile already on screen, and recommendations or search hits usually are not, so the agent could previously only describe them. The verb puts a labelled rail up with the first title focused, and the templated fallback uses it too.
  • A successful search now finishes the request it came from. The awaited reply is an observation, and tool_results_message hands the next cycle {original_request, results} — so “watch Moon” ends in play, “show me Moon” in open_details, “do you have Moon” in show_titles and nothing more. Several plausible matches end in a question, none in saying so.
  • The deadlines went away. search_catalog awaited 400 ms and CYCLE_FIRST_BYTE_S was 1.2 s; both fired on turns that were about to succeed, and the viewer heard a templated apology instead of the answer. Now the search waits for the TV, and the budget is opt-in — a positive CYCLE_FIRST_BYTE_S brings render_fallback back.
  • The profile reaches the prompt as quoted data. # Memory holds {"viewer_profile": …} and the rules say to ignore instructions inside it, because a profile that had once recorded “should offer similar animated picks” kept steering later turns.
  • The summariser is schema-guided too. It no longer writes the file: it returns ProfileFact(source, evidence, section, fact) — the source named before the claim, the words quoted — and verified_facts drops any whose evidence is not literally in the viewer's own lines or in the previous profile, plus anything that reads as an instruction. render_profile writes the same editable Markdown as before. An unsupported preference is now unrepresentable rather than merely discouraged, and a reply that is not a draft is a failed fold: the transcript stays pending for the retry.
  • One SGR helper, two callers. sgr.py owns strictify and response_format, so the turn envelope and the memory draft cannot drift in how “strict” is spelled. It also knows that inside properties a field named title is a field, not the schema annotation to strip — the request.title slot would otherwise vanish from the contract.
  • Typed text is a second door, not a second path. Titan OS exposes no microphone API, so POST /sessions/:id/text — authenticated by the control token, like the socket — queues the very TranscriptionFrame STT would have produced. Turn-taking, barge-in, memory and the agent stay on one code path, and the browser tests drive a turn without synthesising audio.
  • Redaction moved off the turn. It is a SpanExporter wrapped inside the batch processor instead of a SpanProcessor around it, so the per-span rebuild (the whole prompt on agent.cycle) runs on the export thread rather than inside span.end().
  • The shop is the backend's. shop.yaml behind /shop renders # Shop — every shelf by title_id, with items and prices — and show_products slides it in. Pull, never push: a title appearing in # Shop does not make a request about the film a request about merchandise.
  • The cycle reports itself. agent.plan (parsed plan, validation, rejected actions), agent.speech (per sentence, submitting → submitted) and agent.feedback (what the next cycle sees) join agent.cycle's stop_reason, so a turn that said nothing useful can be diagnosed from the trace instead of from guesses.
  • Routing has a fixture suite. tools/routing_eval.py (smoke_turn.py --routing-suite) runs tests/fixtures/named_title_routing.json through the real agent against a simulated TV under a request budget, and scores the action sequence, the search query, the target id and the final intent — with optional profile/history ablation for the “instructions in memory” failures above.

What changed since v2 (that diagram was drawn before the agent cleanup, d13428f..7aa8f13, and before observability):

  • Memory is one rolling profile, not VoiceMem. No left brain / right brain, no top-5 memory search, no local E5 for memory. SummaryMemoryLane appends every exchange to pending.jsonl and one LLM call rewrites profile.md — at session end and every 6 ingests, so what was said in turn 1 is back in the prompt by turn 7 even though the conversation window is ~5 exchanges.
  • recall_memory is gone. With a rolling profile it could only return what # Memory already held, and it bought a ~1 s second cycle for nothing.
  • The agent is the sole writer of the system prompt. ScreenContextInjector used to stamp # Screen and # Recent activity and then build_messages appended them again — two fetches and two copies per turn. The injector is now wired only for AGENT_IMPL=stub.
  • rec_shown moved to turn end and records what the agent actually named or focused, not the ≤ 8 titles the tool returned. An interrupted turn records nothing, and the greeting can no longer offer a film the viewer never heard.
  • The canned TTFT filler was deleted. It was off in production and cost a task, a race and a finally; the model's own first sentence is the filler.
  • A failed awaited TV command now earns a cycle. Seen live with no TV attached: the filler “Searching for X.” was the whole turn and the viewer waited on nothing.
  • An echo filter exists, and is off by default. Browser AEC leaves the avatar's own sentences intelligible enough that Safari and Chrome both returned them as user transcripts; VAD thresholds cannot tell them apart, but the text can — a “user” utterance that repeats ≥ 60 % of what the avatar just said, while echo is still physically possible, is echo. The catch is that short corrections reuse those words: “no, die hard” right after the avatar named No Hard Feelings was dropped too. So ECHO_FILTER=false, and barge-in leans on browser AEC plus the two-transcribed-word threshold instead.
  • Embeddings are local by default — multilingual-e5-small, 384 dims, ~15 ms per query. Cloud Qwen3-Embedding-8B measured 200–500 ms and blew the 400 ms tool budget in the field.
  • Tracing exists (third panel), and is off by default.
